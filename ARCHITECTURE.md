# Architecture

How this project is put together, and why. For a new project this is the
specification to build from; afterwards it is kept true as the project
changes. The rules that apply to every task are in AGENTS.md.

## Current state

M0 (gate-level spike), M1 (software pipeline), M2 (whole-core
simulation) and M3 (linked, steppable views) are built:

- `backend/rtl/` is a single-cycle RV32I core in SystemVerilog (MIT, see
  `docs/core-choice.md`); `synth.ys` synthesizes it with Yosys, keeping
  hierarchy, to the gate set {AND, OR, XOR, NOT, MUX, DFF}.
- `backend/programs/` holds the fixed program `sum.c`, `crt0.S` and `link.ld`.
- `make artifacts` regenerates everything in `backend/artifacts/`, which is
  committed: the hardware artifacts `netlist.json`, `gate_counts.json`,
  `adder_values.json` and `toolchain.json`, and, for each program in
  `backend/programs/`, a folder named after it (`sum/`) holding
  `program.json`, the hex image, `golden.json` and `trace.json`.
- The API serves those artifacts and builds per-cycle views from them; the
  page (`src/web/`) shows C, assembly, machine code and the hardware (opening
  on the datapath) for any cycle, with stepping by cycle or by C line. It
  opens on the cycle `/api/start` names (see Backend).
- `make regression` plants the defects in the answer key
  (`src/app/regression_key.py`) and checks what catches each.

Not built yet: gate-level views of the large modules (M4): the ALU shifter
and result mux, the load/store unit, the PC adders, and the ALU's glue logic.

## Stack

- Backend: Python 3.14 (base image `python:3.14.10-slim-trixie`, pinned by
  digest like every base image, so a tag moving upstream cannot change the
  build; `make base-digests` prints the current digests when upgrading) and FastAPI, with typed request and response models; `/docs` is the
  contract.
- Frontend: static HTML and JavaScript, with no build step for our own code.
  It uses whichever library suits the view (Plotly for plots, D3 for custom
  charts, three.js for 3D); the plan names it and says why. The page uses
  elkjs (`docker/package.json`) to place boxes and route wires for views
  generated from the netlist; it never computes a value. The adder's
  textbook drawing is SVG rendered by the backend (`src/app/render.py`).
- Headless Chromium (Debian `chromium-headless-shell`) is in the image only
  for `make smoke` and `make screenshot`. Debian's security updates delete old
  Chromium builds from the archive, so it is pinned to an exact build through
  snapshot.debian.org (`CHROMIUM_VERSION` and `CHROMIUM_SNAPSHOT` in the
  Dockerfile).
- Hardware and software tools, all pinned in `docker/Dockerfile`: Yosys
  (built from a release tag), Spike (built from a commit), and Debian's
  `gcc-riscv64-unknown-elf`, `binutils-riscv64-unknown-elf` and `iverilog`
  (exact package versions). `toolchain.json` records what each tool reports.
- Everything runs in one development container, as the host user.

## Backend

- One pipeline per API endpoint, each with one entry-point function in
  `pipeline.py`. The API calls it; tests may call any function.
- Two kinds of entry point. `build_*` run offline (`make artifacts`) and
  call the tools: `build_hardware_artifacts` (Yosys synthesis, gate counts,
  Yosys `sim` of the adder) and `build_program_artifacts` (compile, objdump,
  hex image, Spike), then `build_trace_artifacts` (M2). `get_*` serve one
  endpoint each from the committed artifacts and recompute nothing except
  the drawings.
- Programs are named after their C file (`sum`). Every per-program `get_*`
  and API endpoint takes the name (`?program=`, default `sum`, validated);
  `/api/programs` lists them, and an unknown name is a 404. The page reads
  it from the URL (`#program=sum&cycle=11&view=...`).
- Values on the gates come from Yosys `sim` on the synthesized netlist
  (`build_trace_artifacts`), with the register file and RAM replaced by
  their behavioural models. Icarus Verilog runs the RTL as an independent
  reference; it is used only to verify, never shown. Python only reads the
  VCD files the simulators write.
- Both runs are sampled once per cycle, just before the rising clock edge,
  with reset cycles left out, so cycle n is instruction n of golden.json.
- `trace.json` is written only after every check passes (gate vs RTL on
  every common signal, no x/z, every instruction vs Spike, x0, halt cycle);
  a failure names the first cycle and signal that differ.
- Programs outside the C subset raise `ProgramRejected` with one plain
  message (file and line where known). Checks: the preprocessed source
  (no float/double, no `*` `/` `%`), the linker (undefined libc symbols,
  RAM overflow) and Spike (no halt within 500 retired instructions).
- Views: `views.py` turns any module of the netlist into a graph (its
  ports, blocks or gates, constants, and the wires between them, each wire
  naming its trace signal and bit range) with values for one cycle. Modules
  made only of gates get one pin per bus bit; a block view with more than 40
  loose gates groups them into one "glue logic" node. Which modules open, and
  how, is set by `GATE_MODULES` and `BLOCK_ONLY` there.
- Programs compile with `-march=rv32i -mabi=ilp32 -Og -g -nostdlib
  -ffreestanding` (`-O1` folds `sum.c` to a constant; see README).
- Halt convention: `crt0.S` stores `(a0 << 1) | 1` to `tohost`. Spike exits
  with a0; the golden log ends at that store.
- The start cycle (`views.start_cycle`, served by `/api/start`) is where the
  program first loops back: the cycle after a branch or plain jump (`jal
  zero`) to a lower address in the same function, both cycles on C lines.
  Calls and returns do not count. Else the first cycle on a C line, else 0.
  Nothing in it is specific to `sum.c`, so M5's user programs open the same
  way. The page says why it opened there only when no link chose the cycle.
- `make regression` copies the repository to
  `backend/build/regression/<plant>/`, makes one plant's edit there, and runs
  that copy's `app.cli artifacts`, `pytest` and `app.smoke` (against a server
  from the copy on port 8001, its output in the copy's `server.log`) until
  one fails. The answer key names the stage and message that must catch each
  plant, or none for a known blind spot, which must then still have changed
  the rebuilt design artifacts. A stage that cannot run (a server that never
  answers) counts as failing there; the other plants still run.
  `tests/test_regression_key.py` fails as soon as a plant's text no longer
  occurs exactly once, so the key cannot drift from the code silently.
- `api.py` holds routes only. It also serves our page from `src/web/` and the
  frontend libraries under `/vendor/`.
- Errors reach the page as one plain message, and the page clears any earlier
  result when it shows one: a stale plot never sits beside an error.

## Design patterns and interfaces

Named in README ("How the code is organized") and enforced by
`tests/test_architecture.py`:

- `pipeline.py` is a facade: `api.py` and `cli.py` (the two adapters) import
  only it plus `models`, `errors` and `paths`.
- The steps (`software`, `hardware`, `simulate`, `views`, `render`, `decode`,
  `vcd`, `tools`) never import the facade, the adapters or the checks.
  The checks (`smoke`, `pagecheck`, `regression`) are adapters too.
- Only `tools.py` starts external programs (`run_tool`, `ToolStream`).
- The page fetches through one helper, and only from `/api/`.

## The container

- The Dockerfile has six stages. Two tool stages, one with uv and one with
  Node, are where `make lock` runs, so the first lock needs no lock. A third
  installs the frontend libraries from `package-lock.json`. Two build stages
  compile Yosys and Spike from pinned sources. The final image holds the
  RISC-V GCC and binutils packages, the Python dependencies from `uv.lock`,
  the frontend files from the third stage, and the Yosys and Spike installs.
  The first `make build` takes a while (Yosys is a large C++ build).
- The image never copies `src/`. The repository is mounted at `/work`, with
  `PYTHONPATH=/work/src`.
- Frontend libraries are installed at build time from `package-lock.json` and
  copied into the image outside `/work` (the mount would hide them). Never
  installed on the host, never committed, never loaded from a CDN.
- `compose.yaml` publishes on `127.0.0.1` and runs as the host user (its user
  and group IDs passed in by the Makefile; 1000 on Windows, which has no
  such IDs), with `HOME` set to a writable directory inside the container
  for the tools' caches.
- The Makefile names the compose project after the repository directory
  (`COMPOSE_PROJECT_NAME`), so two projects never share containers or images.
- `.env` holds plain `KEY=value` lines, without quotes; the Makefile includes
  and exports it, because compose pointed at `docker/` would not find it.
- Portable: the image builds natively on amd64 and arm64 (every apt pin
  exists on both), and Makefile recipes are POSIX sh, so they run on Linux,
  macOS and Windows (Git Bash). `.gitattributes` keeps LF endings on every
  checkout, because the committed artifacts are compared byte for byte;
  `tests/test_portability.py` fails with the real cause if they are not.

## Makefile

`make help` (the default) lists every target in four groups.

Everyday, the only ones a user needs:

- `pull`: download the image CI built and verified for this checkout
  (`ghcr.io/alekfarmer/ee292m-capstone:<tag>`; set `IMAGE_REPO` to use
  another registry). The tag is a fingerprint of the files the image is built
  from (the Dockerfile, both manifests and both locks;
  `tests/test_image.py` fails if the Dockerfile copies a file it does not
  cover), so a pulled image was built from this checkout's `docker/`; with no
  match, it says to run `build`. The base images are pinned by digest, but
  some Debian packages are taken at their current version, so two builds of
  one tag can still differ there.
- `build`: build everything the project needs, into the image. Skipped when
  the image there already carries this checkout's fingerprint (compose labels
  every build with it), so a pulled image is never rebuilt.
- `up` and `down`: start and stop the app.
- `verify`: check that it all works (lint, test, smoke). Must pass from a
  fresh clone with only Docker, Make and git installed.
- `clean`: return to the state of a fresh clone. This project's containers,
  images and generated files are removed; `data/raw/` and `.env` are kept, and
  so are the base images and build cache Docker shares with other projects.

While developing:

- `artifacts`: regenerate `backend/artifacts/` (M0–M2, every program). The tests
  rebuild everything into a temporary directory and fail if the committed
  artifacts differ.
- `preview`: write the adder drawings to `backend/build/preview/` (to look
  at the SVG outside the app). `synth-log`: run synthesis alone with the
  full Yosys log in `backend/build/synth.log`.
- `screenshot`: start the app and save screenshots of a few views to
  `backend/build/screenshots/` (headless Chromium in the container).
- `test`: run the tests (`ARGS=...` is passed to pytest). `lint`: check the code, changing nothing. `fmt`:
  rewrite the code into the standard format.
- `smoke`: start the app, check a real API result (not just a status code),
  stop it again.
- `regression`: plant each defect in the answer key and check that the stage
  the key names catches it (`PLANT=name` for one), in about 30 seconds.
- `logs` and `shell`: follow the app's output; open a shell inside the
  container.

Only when dependencies change:

- `lock`: after adding, removing or upgrading a package in
  `docker/pyproject.toml` or `docker/package.json`, record the exact versions
  in `docker/uv.lock` and `docker/package-lock.json`, and commit each manifest
  with its lock. `build` uses only what the locks record, and says so, with
  this instruction, when a manifest and its lock disagree.
- `base-digests`: print the digest of each base image the Dockerfile starts
  from (by the tags in the Makefile's `BASE_IMAGES`), to pin when upgrading
  one.

CI only (`.github/workflows/verify.yml`):

- `publish`: push this machine's image as `<tag>-amd64` or `<tag>-arm64`;
  CI runs it on main only, after `verify` and `regression` passed.
  `publish-manifest`: join the two under `<tag>`, so `pull` gets the right one
  for each machine.

Every target runs through compose (`docker compose -f docker/compose.yaml`).
